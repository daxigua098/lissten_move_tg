## 一句话方案

一套面向 Telegram 群组/频道运营的「**内容搬运（A 线）+ 会员线索生产（B 线）**」系统：

- **A 线**：把源频道/群的帖子（只要文字、图片、视频）净化后搬到自己的频道，按频率附加自家广告。
- **B 线**：监听源群成员发言，按全量或关键词命中生成含联系方式与私聊入口的线索卡片，推送到指定群并入库。

## 已确认的关键决策

| 编号 | 决策 |
|---|---|
| D-01 | 业务规则挂在"线路"上；同一源可并存多条线路，可发给不同群组 |
| D-02 | 控制 Bot 只做指令与通知；采集与投递全部依赖执行账号，账号支持 1–N 个 |
| D-03 | A 线只搬文字/图片/视频，剥离对方链接、@提及、按钮与推广词行 |
| D-04 | 广告只作用于 A 线；策略可选每条或每 N 条，默认每 3 条 1 条 |
| D-05 | 历史补齐以"线路 × 目标"记录水位线，新增目标只补自身，老目标零重复 |
| D-06 | B 线默认全量监听且只入库不推卡片；命中关键词才推卡片 |
| D-07 | 数据保留 3 天（原文 / 档案 / 线索），长期仅保留不含原文的"触达指纹" |
| D-08 | 清理前自动归档为 NDJSON 压缩包，默认保留 30 天 |
| D-09 | B 线不自动私聊；只给联系方式和私聊入口，由人工或下游发送系统处理 |
| D-10 | 监听账号与下游发送账号物理隔离，绝不混用 |
| D-11 | 数据源销售采用形态 2：中心采集 + 数据流分发 |
| D-12 | 私有部署由供方代部署，执行账号客户自备 |
| D-13 | 离线授权码（签名 + 机器指纹），模块开关控制搬运/监听/订阅 |
| D-14 | GitHub Actions 只做部署流水线，运行依赖 Linux systemd 常驻服务 |

## 本地运行

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt -r requirements-dev.txt
Copy-Item .env.example .env      # 按文件内注释生成并填入 SECRET_KEY
python main.py check-config
pytest -q
ruff check .
```

> 说明：本项目尚未单独创建 `.venv`。当前 T1-01 的测试与 lint 是复用同级旧项目 `telegram搬运监听\.venv` 的解释器执行的（该环境已具备 pydantic / loguru / pytest / ruff 等依赖）。T1-02 需要 Alembic，届时建议为本项目创建独立虚拟环境并安装 `requirements.txt`。

> 更新：项目已自建 `.venv`（Python 3.13），依赖按 `requirements.txt` 安装完毕；后续命令请用 `.\.venv\Scripts\python.exe` 或先激活虚拟环境。

## 本地部署（当前可用）

```powershell
# 一键启动（首次会自动构建前端、迁移数据库、创建管理员）
.\scripts\start-local.ps1

# 后台运行 / 停止
.\scripts\start-local.ps1 -Background
.\scripts\stop-local.ps1
```

浏览器打开 <http://127.0.0.1:8000>，用 `admin / admin123` 登录（默认密码在 `.env` 的 `ADMIN_PASSWORD` 中维护）。

> 手动步骤等价于：`main.py check-config` → `main.py init-db` → `main.py create-admin` → `frontend` 目录 `npm run build` → `main.py api`。
> 注意：服务必须在**你自己的终端**里启动。通过隔离环境启动的服务，桌面浏览器可能无法访问 127.0.0.1:8000。

已可用的功能：登录与会话、三级角色权限、审计日志、登录历史、账户管理（新增/改角色/启停/重置密码/踢下线/删除）、运行总览（真实数据来自 `/api/system/status`）。

E3 新增：执行账号池（登记 / 凭据加密 / 状态与健康度 / 默认账号）、控制 Bot（Token 实时校验 / 多 Bot / 默认切换 / 管理员白名单）、Telegram 链接解析（`t.me/xxx`、`@xxx`、邀请链接、数字 ID）。

E4 新增：监听源与接收组的左右穿梭框、从执行账号同步已加入的群组池、粘贴链接添加（含私有邀请需显式允许加入）、源/接收组各自独立的启停开关、批量与单个标签维护、接收组用途（内容接收 / 线索接收）与发言权限预检。

E5 新增：线路模型（源 + 业务类型 + 规则 + 多目标）、矩阵快速建线（同批源 × 同批目标，已存在自动跳过）、按业务类型动态渲染的线路编辑器、目标级水位线（新增目标只补自己缺的、老目标零重复）、重置进度需输入 RESET、广告素材库（文案 + 图片 + 链接按钮、变量插入、发送效果预览、被引用保护、停用优先于删除）。

广告素材支持**本地上传图片**：JPG / PNG / GIF / WEBP，最大 5 MB，服务端会用 Pillow 校验真实格式与尺寸，落盘为随机文件名存到 `assets/uploads/`，可通过 `/uploads/<文件名>` 直接访问；上传目录已被 `.gitignore` 排除。

> A 线配置：内容类型、净化规则（链接/@提及/按钮/电话/推广词行）、copy 或 forward、相册聚合、广告频率与素材、历史补齐范围与速率。

E6 新增：净化引擎（剥链接、@提及、电话、推广词行，含空文本策略）、投递引擎（幂等入队、串行队列、失败指数退避重试、至少一次投递）、广告附加（每条 / 每 N 条，计数按线路+目标+当天独立）、历史补齐（**目标级水位线**：新增目标只补自己缺的，老目标零重复）、实时监听（NewMessage 入队同一队列）、运行时锁与心跳（防多实例、暂停/恢复/停止开关）。

新增 CLI：

```powershell
python main.py sync-history --all        # 补齐 A 线历史消息
python main.py run                       # 启动搬运运行时（实时监听 + 串行投递）
python main.py status                    # 运行时状态与投递统计
python main.py pause / resume / stop     # 运行控制
```

> 文案处理有两种模式：`keep` 直接转发（快，保持原文）；`clean` 净化后重新上传媒体并替换文案（慢，但真正去掉对方的广告链接与推广词）。转发方式无法修改原文，所以「净化文案」必须走重新上传。
> B 线配置：全量或关键词监听、关键词组、敏感度（宽松/标准/严格）、匹配方式（包含/模糊/语义）、排除词、发言人过滤、字数门槛、去重窗口、资料抓取与卡片模板。
> 两条业务线都做了"选了但不能为空"的校验：A 线挂广告必须选素材，B 线关键词模式必须有词组。

> 绑定执行账号后还要在服务器上做一次交互登录：`.\.venv\Scripts\python.exe main.py account-login --name 别名`（会提示输入验证码与两步验证密码）。
> 绑定控制 Bot 需要先配好 `TG_API_ID` / `TG_API_HASH`（写进 `.env`），否则校验会返回明确提示。
